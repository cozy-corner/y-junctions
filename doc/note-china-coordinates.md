# 中国の火星座標と、写真のないY字路

Y字路を地図上で探せるサービスを作っています。OpenStreetMap のデータから、道がYの字に分かれている場所を抽出して地図に並べたものです。2025年末に関東から始めて、日本全国、台湾、韓国と収録範囲を広げてきました。

サービスはこちら: https://storage.googleapis.com/y-junctions-prod-frontend/index.html

次は中国本土を入れようと思い、今年の4月に上海から手を付けました。他の地域とは手順がかなり違ったので、その記録を書きます。技術的な解説というより、地図データが国によってこうも違うのか、という話です。

## 中国では Google ストリートビューが使えない

Y字路は、写真で見ないと面白くありません。このサービスでも、マーカーをクリックすると Google ストリートビューが開いて、その角が実際にどうなっているかを見られるようにしています。

ところが中国本土には、Google ストリートビューがありません。調べた範囲では、こういう状況でした。

| サービス | 中国本土のカバレッジ |
|---|---|
| Google ストリートビュー | なし |
| Bing Streetside | なし |
| Mapillary（有志が撮った写真を共有するサービス） | ほとんど無い |
| 百度地図の「全景」 | 最も充実している |

つまり百度一択です。幸い、百度の全景は日本からでも普通に見られます。

全景というのは、Google ストリートビューと同じで、撮影車が道を走りながら撮った360度写真です。1枚ずつに固有のID（パノラマID）が振られていて、これさえ分かれば、その写真を開くURLを組み立てられます。

手順としては、Y字路の緯度経度を百度に投げて「その地点に一番近い写真はどれか」を教えてもらい、返ってきたパノラマIDを保存しておく。地図でクリックされたら、そのIDのURLを開く。これだけです。

## 座標をそのまま渡すと、数百メートル先を指す

ただし、Y字路の緯度経度をそのまま投げると、街区をいくつかまたいだ先の写真が返ってきます。原因は、こちらが渡す緯度経度のほうにあります。

中国で公開されている地図データは、GPS が出す緯度経度（WGS84）とは別の座標系で作られています。GCJ-02、2002年に国家測絵局が定めたもので、WGS84 に対して場所ごとに違う量のズレが加えてあります。GPS の点をそのまま中国の地図に置くと 100〜700メートルずれる、というのが一般に言われている数字です。

この座標系には「火星座標」という通称があります。GPS のとおりの場所にいるはずなのに、地図の上では別の場所になる。まるで違う惑星にいるようだ、というのが由来だと言われています。

自分の実装で計算してみると、こうなりました。

| 場所 | ズレの大きさ |
|---|---|
| 上海・人民広場 | 約481 m |
| 北京・王府井 | 約555 m |
| 広州・天河 | 約625 m |
| 成都・春熙路 | 約361 m |

ズレる量は場所によって違い、方向も一定ではありません。地図全体を平行移動しているのではなく、緯度経度を入れると歪んだ値が返ってくる式になっているためです。

## ズレているのはこちらの座標

ここで「百度の地図がズレているのだから、こちらで補正してやればいい」と考えたくなるのですが、これは違います。

百度の世界の中では、何もズレていません。地図タイルから衛星写真、店舗の位置、全景の撮影地点、ルート検索の距離計算まで、すべてが同じ座標系で作られています。全部が同じだけ歪んでいるので、百度地図を普通に使っているぶんには矛盾が起きません。中国国内でカーナビを使っても、目的地にちゃんと着きます。

ズレが出るのは、外から素の GPS 座標を持ち込んだときだけです。ズレていたのは向こうの世界ではなく、こちらが持ち込んだ数字のほうでした。

ということは、書くべき処理は「ズレを直す」ものではありません。国が加えたのと同じ歪みを自分の点にも加えて、向こうの世界へ着地させる処理です。正しい座標を、わざとずらした座標に変換することになります。方向としては逆なので、なかなか直感に反します。

実際の変換は三段構えになります。

1. 一段目は、GPS の座標を GCJ-02（火星座標）に歪ませる。国が定めた分です
2. 二段目で、百度が独自にかけている歪みをさらに足します
3. 三段目で、百度が地図の内部で使っているメートル単位の座標に投影します

国が一段、企業がもう一段、歪みを重ねている構造です。百度が独自にかけている理由は「ユーザーのプライバシーを保護するため」と説明されています。

## 式は公開されていない

この歪みの計算式は、公開されていません。中国で電子地図を作るには「導航電子地図制作」の資格が要り、国（現在は自然資源部）の審査を通った事業者だけが名簿に載ります。式は、その中で使われるものという建て付けです。

実際に書いたコードが、これです。一段目、GPS の座標を火星座標に歪ませる部分から、緯度方向だけを抜き出しています。経度のぶんも、定数が違うだけの同じ形の式がもう一つあります。

```rust
fn gcj_transform_lat(x: f64, y: f64) -> f64 {
    let mut ret = -100.0 + 2.0 * x + 3.0 * y + 0.2 * y * y + 0.1 * x * y + 0.2 * x.abs().sqrt();
    ret += (20.0 * (6.0 * x * PI).sin() + 20.0 * (2.0 * x * PI).sin()) * 2.0 / 3.0;
    ret += (20.0 * (y * PI).sin() + 40.0 * (y / 3.0 * PI).sin()) * 2.0 / 3.0;
    ret += (160.0 * (y / 12.0 * PI).sin() + 320.0 * (y * PI / 30.0).sin()) * 2.0 / 3.0;
    ret
}
```

-100、20、40、160、320。どこから来た数字なのか、なぜ 2/3 を掛けるのか、まったく説明がありません。三角関数をいくつも重ねて、不規則にずらしています。ズレの量が場所ごとに違うのは、この sin の重ね合わせのせいです。

自分で解いたわけではありません。この式はネット上に出回っていて、中国の地図を扱う人はそれを自分の言語に書き写して使います。今回のコードも、係数の一桁に至るまでそれと同じです。

出どころについては、[英語版 Wikipedia](https://en.wikipedia.org/wiki/Restrictions_on_geographic_data_in_China) が、GPS の座標から火星座標への部分は「流出したコードに基づくとみられる」と書いています。誰も式を知らないことになっているのに、同じ式が世界中にコピーされて動いています。

ちなみに、その次に百度が足している歪み（二段目）は、これだけです。

```rust
pub fn gcj02_to_bd09ll(lng: f64, lat: f64) -> (f64, f64) {
    let x_pi = PI * 3000.0 / 180.0;
    let z = (lng * lng + lat * lat).sqrt() + 0.00002 * (lat * x_pi).sin();
    let theta = lat.atan2(lng) + 0.000003 * (lng * x_pi).cos();
    (z * theta.cos() + 0.0065, z * theta.sin() + 0.006)
}
```

こちらも百度が公表している式ではありません。ただ、流出したという話が出てくるのは一段目のほうで、こちらについてはそういう説明を見かけません。一段目に比べると式が短く、少し回してから決まった量をずらすだけだからだと思います。

ただ、式が短いこととズレが小さいことは別でした。0.0065 と 0.006 は度の単位なので、上海の緯度だと合わせて 900 メートルほどになります。

つまり、上海のY字路の座標が最終的にどれだけ動くかというと、こうです。

| 段 | 上海でのズレ |
|---|---|
| 一段目（国が定めた分） | 約481 m |
| 二段目（百度が足した分） | 約901 m |
| 合計 | 約1,140 m |

先に挙げた「100〜700メートル」は一段目だけの話です。百度の地図に載せるには、その上にもう一段ぶん動きます。国が加えた歪みのほうが有名ですが、量でいえば企業が足したぶんのほうが大きいわけです。

逆方向、つまり中国の座標を GPS の座標に戻すほうは、式を解いて一発で求めることができず、繰り返し計算で近づけることになります。よく使われている [eviltransform](https://github.com/googollee/eviltransform) という実装では、精度は 1〜2メートルと書かれています。今回は順方向だけで足りたので、逆変換は実装していません。

なぜこんな仕組みがあるのかは、公式には国家安全のためと説明されています。制度としては、中国で地図を公開・販売・配信する前に「空間位置技術処理」をかけることが求められていて、地図を出せるのは認可を受けた事業者に限られます。[英語版 Wikipedia](https://en.wikipedia.org/wiki/Restrictions_on_geographic_data_in_China) によれば、このアルゴリズムの利用にはライセンス料もかかるそうです。都市伝説ではミサイル避けと言われますが、実際に効いているのは、地図を出せる事業者を国が管理するという部分だと思います。

私自身は地理にも中国の制度にも詳しくないので、このあたりは調べた範囲で書いています。詳しい方から見ると不正確な部分があるかもしれません。

## 公式の API が無い

もう一つ、地味に手間だったのが、このパノラマIDを集める作業です。

百度には開発者向けの地図APIがあるのですが、「この座標に一番近い全景はどれか」を返してくれるものが見当たりませんでした。結局使ったのは、百度地図のページが内部で叩いているURLです。APIキーは要らず、座標を投げると `09000300122101111452570287I` のようなパノラマIDが返ってきます。ドキュメントはありません。

正規の使い方ではないので、相手に負荷をかけない工夫が要ります。実装しながら足していったのは、こういうことでした。

- **ブラウザからのアクセスに見せる**。リクエストには、どんなソフトから来たかを示す User-Agent という項目が付きます。ここが見慣れない値のままだと弾かれたので、Chrome のものを入れました
- **リクエストの間隔をばらつかせる**。きっちり等間隔で叩くのは、人間ではないと言っているようなものです。80〜150ミリ秒の範囲でランダムに待ちます
- **断られたら引き下がる**。「多すぎる」と返ってきたときは、向こうが指定してきた秒数だけ待ってからやり直し、それでも駄目ならバッチごと止める。無理に続けても良いことはありません
- **同じことを二度聞かない**。「ここは全景が無い」という答えも記録しておいて、次に走らせたときには問い合わせ自体をしない。無いものを毎回聞きに行っても、お互い無駄なだけです
- **100件ごとに保存する**。途中で通信が切れても、そこまでの成果が消えないようにしています

最後の2つは、要は同じ座標を何度も聞かないための仕組みです。4,350件を1件ずつ順番に、1件あたり0.1秒ほど空けて聞いていくので、全部終えるのに10分ほどかかります。やり直すたびに最初から聞き直していては、相手にとっても迷惑ですし、こちらもいつまでも終わりません。

こうした非公式な経路は、いつ使えなくなってもおかしくありません。閉じたときは中国のY字路から写真のリンクが消えるだけで、他の地域には影響しない作りにしてあります。

## 結果、上海のY字路は74%

上海の市街地から抽出できたY字路は 4,350件。そのうち、近くに全景が見つかって写真を開けるようになったのは 3,222件、約74%でした。

残りの 1,128件は、百度の撮影車が通っていない道でした。地図上には道として存在し、Y字路としても抽出できているのに、写真だけありません。細い路地や、車が入れない道が多いのだと思います。

この「見つからなかった」の判定には少し工夫が要りました。百度に座標を投げると、多少離れていても近くの写真を返してくることがあり、そのまま採用すると隣の通りの景色にリンクしてしまいます。そこで、返ってきた写真の撮影地点が元のY字路から 10メートル以上離れていたら捨てることにしました。撮影車が走りながら撮っている以上、それより細かい間隔にはならないだろう、という見当です。

74%を高いと見るか低いと見るかは微妙なところです。日本ではほぼ全部にリンク先がある前提で作っていたので、「飛ばす先が無いY字路」という状態を初めて真面目に扱うことになりました。マーカーは地図に出すけれど、ストリートビューのボタンは出さない。それだけの話ではあるものの、それまでのコードにはその状態自体が存在していませんでした。

## おわりに

この作業をするまで、緯度経度というのはどこでも同じように使える普遍的な数字だと思っていました。GPS が出す数字を地図サービスに渡せば、その場所が出てくる。当たり前だと思っていたわけです。

そうはならない国がありました。しかも国の中では何も破綻していなくて、破綻するのは外から素の数字を持ち込んだときだけです。向こうの世界に入るには、こちらが歪まなければならない。

やったことは座標変換を1つ書いただけですが、地図データというものが思っていたよりずっと制度と地続きなのだと知る作業でもありました。

上海はあくまで試験的な追加で、中国本土に広げられるかを見るために市街地だけを入れたものです。

そして、いまのところ他の都市に広げる予定はありません。理由は精度やデータ量ではなく、速度です。日本から百度地図を開くと、グレートファイアウォールを越える通信になるためか、表示までかなり待たされます。マーカーをクリックして景色が出るまで待たされるのでは、Y字路を眺める体験としては成立しません。上海のデータを入れてみて、そこが一番の壁だと分かりました。
