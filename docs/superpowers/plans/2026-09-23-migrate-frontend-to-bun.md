# Frontend Tooling Migration: npm → bun Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace npm-based frontend tooling with bun (via mise-pinned version) across local dev, pre-commit hooks, CI, deploy, and docs. Backend (Rust/Cargo) is out of scope.

**Architecture:** Pin bun via `[tools]` in `.mise.toml`. Replace `package-lock.json` (root + frontend) with text-format `bun.lock` generated by `bun install`. Update husky, lint-staged, GitHub Actions, dependabot, mise tasks, and README in lockstep. Verify each layer locally before promoting.

**Tech Stack:** bun (>= 1.2 — text `bun.lock` is the default only from v1.2; `mise ls-remote bun` latest stable is 1.4.2), mise, GitHub Actions (`oven-sh/setup-bun@v2`), husky, lint-staged, Dependabot.

**Spec:** This plan was originally drafted against an external design note (`HANDOFF-bun-migration.md`). That file is not present in the repo, so all design decisions live in the "Open decisions" section below — every item the handoff would have covered has been resolved inline.

## Global Constraints

- Bun version chosen at Task 1 and used consistently across `.mise.toml`, GitHub Actions `bun-version:`, and `package.json` `packageManager` field.
- No changes to `backend/Dockerfile`, `pipeline/Dockerfile`, `backend/src/**`, `pipeline/**`, or any Cargo file.
- Conventional Commits subject line: `chore(deps): migrate frontend tooling from npm to bun`.
- **Environment prerequisites.** This plan's commands assume bun is on PATH (>= 1.2, text-format `bun.lock` default from v1.2+). mise is required for Task 2 (pin via mise) but optional elsewhere — in any env where bun is already on PATH, drop the `mise exec --` prefix and run `bun` directly.
  - HOST (Mac): bun via `mise install`. Use `mise exec -- bun ...` for explicit version pinning.
  - pi-coding-agent (Gondolin VM): bun 1.4.2 ships at `/usr/local/bin/bun` in this VM. **No mise** — run `bun` directly (no `mise exec --` prefix). Local verification (Tasks 5–7, 12) can run here. Pushing the branch and `gh pr create` must run on HOST (VM has no git push auth / SSH keys for GitHub).
- Text-format `bun.lock` only. Do not commit `bun.lockb`. Per Bun docs, `bun.lock` has been the default since **v1.2** — so the pinned version MUST be >= 1.2, otherwise `bun install` emits the binary `bun.lockb` and Task 5's format gate fails.
- **Plan self-check before starting.** Run `bun --version` once; if it returns < 1.2, stop and pin a newer version in Task 2. The current pin candidate (1.4.2) and the VM's installed version (1.4.2) both satisfy the constraint.

## Open decisions (resolve in Task 1)

1. **bun version** — pick latest stable from `mise ls-remote bun` output; must be >= 1.2 (see Global Constraints). As of 2026-09-26 the latest stable is **1.4.2**. Record in Task 1.
2. **issue number** — find or create the GitHub issue. Pass to commit message and branch name.
3. **`.lintstagedrc.json` commands** — change `npm run` → `bun run` for consistency (the handoff's claim that "npm run is bun-compatible" is wrong; they are separate binaries — npm remains installed but mixing both creates inconsistency). **Decision: switch to `bun run`.**
4. **Root `package.json` scripts** (e.g. `frontend:dev` → `cd frontend && npm run dev`) — leave as `npm run`. These are convenience wrappers from root, npm is still installed, and changing them expands scope without value. **Decision: no change.**
5. **Dependabot for bun.lock** — Handoff missed this. **Resolved (2026-09-26):** Verified via GitHub docs that `package-ecosystem: "bun"` is supported for bun >= v1.1.39; Task 11 switches the frontend ecosystem. Root stays on `npm` ecosystem (out of scope).

## Review Focus

Inputs / failure modes the spec implies but no single task exercises. Each line names the failure and points to the test that pins it.

- **CI cache invalidation on lockfile rename** — first CI run after merge may have a cold cache because `cache-dependency-path` changed from `package-lock.json` to `bun.lock`. Expect ~2x install time on first run. Pinned in Task 14 (CI watch step) by checking install times.
- **`oven-sh/setup-bun@v2` default version drift** — if no `bun-version:` is set, action uses default; missing version causes silent inconsistency with mise pin. Pinned in Tasks 8 and 9 (each `Setup Bun` step explicitly sets `bun-version`).
- **Vitest still uses Node-style resolution** — `bun run test` invokes vitest which still does its own resolution. Note bun does not fail on Node-only postinstall scripts; it *blocks* them by default (`trustedDependencies` opts in), so a dep whose native build never ran surfaces later as a runtime/build error, not an install error. Pinned in Task 5 Step 2b and Task 6 Steps 4-5.
- **Dependabot stops watching frontend deps** — if dependabot.yml isn't updated alongside lockfile, weekly PRs stop and security updates go unseen. Pinned in Task 11 (switched to `bun` ecosystem; supports bun >= v1.1.39).
- **Husky invocation after `.husky/pre-commit` change** — `bunx lint-staged` requires `bunx` on PATH (mise-installed bun provides it). If mise trust hasn't run on the new worktree, pre-commit silently uses the system npx. Pinned in Task 6.

## Task 5: Migrate lockfile (frontend + root)

**Files:**

- Delete: `/workspace/package-lock.json`
- Create: `/workspace/frontend/bun.lock` (generated by `bun install`)
- Create: `/workspace/bun.lock` (root, generated by `bun install`)

**Interfaces:**
- Produces: text-format `bun.lock` files at root and in frontend. GitHub Actions will read these in Task 7/8.

- [ ] **Step 1: Remove old lockfiles and node_modules**

Run on HOST in the new worktree:
```bash
rm -rf node_modules frontend/node_modules
rm -f package-lock.json frontend/package-lock.json
ls package-lock.json frontend/package-lock.json 2>&1   # expect: No such file
```

- [ ] **Step 2: Generate bun.lock in frontend**

```bash
cd frontend
bun install
ls bun.lock   # expect: exists
head -1 bun.lock   # expect: text lockfile header (e.g. comment line), NOT binary
# `file` may be unavailable on minimal VMs; use this portable check instead:
head -c 4 bun.lock | od -c | head -1   # expect: printable ASCII (e.g. `-   -   -   -` or `//` ), NOT binary control bytes
command -v file >/dev/null && file bun.lock   # optional: if `file` is installed, expect ASCII text
```

**Verification gate:** if either check reports binary or the install fails, STOP. A binary lockfile means the pinned bun is < 1.2 — fix Task 2 rather than working around it (`bun install --save-text-lockfile --lockfile-only` also converts, per `bun install --help`). Do not proceed.

- [ ] **Step 2b: Check skipped lifecycle scripts**

Bun does **not** run dependency `postinstall`/lifecycle scripts by default (docs: `https://bun.com/docs/pm/cli/install` — "Bun does not execute arbitrary lifecycle scripts like `postinstall` for installed dependencies"). So the failure mode is *silent skipping*, not an install error.

```bash
bun install 2>&1 | grep -i -e blocked -e "trustedDependencies" -e "scripts" || echo "no script warnings"
```
If bun reports blocked scripts for a package the frontend actually needs (esbuild and sharp are auto-handled by bun), add it to `trustedDependencies` in `frontend/package.json` and re-run `bun install`. Record which packages were added.

- [ ] **Step 3: Generate bun.lock at root**

```bash
cd ..
bun install
ls bun.lock   # expect: exists
head -1 bun.lock
```

- [ ] **Step 4: Commit**

```bash
git add -A   # bun.lock files + node_modules is gitignored (verify with `cat .gitignore | grep node_modules`)
git status   # confirm no node_modules staged
git commit -m "chore(deps): replace npm lockfiles with bun.lock"
```

Expected: commit contains only `bun.lock` files at `/workspace/bun.lock` and `/workspace/frontend/bun.lock`. No `node_modules`, no `bun.lockb`.
